**A number in a JSON or YAML artifact is read as the digits the file wrote.** Both loaders hand a number with a fraction or an exponent over as a binary float, and the float was printed back before the comparison: `0.910` became `0.91`, `1e-7` became `1e-07`, and three kinds of value were compared wrongly. A value of more than seventeen significant digits was compared as its nearest double, so a manuscript printing all twenty digits of `0.12345678901234567890` was a `mismatch` against the file it was copied from. `9007199254740993.0` was read as `9007199254740992.0`, which verified the wrong integer and refused the right one. `1e400` was infinity and `value_not_numeric`, and `1e-400` was zero. The text of the number is now kept and read as an exact decimal, and it is what `repro why` and a re-run's record show; `repro verify` prints the same digits, trailing zeros included, with an exponent in the form `1E-7`. Integers were already exact. Against a printed value nothing else changes: the precision is the manuscript's, so `0.910` in a file still verifies a printed `0.91`. A `correspondence` compares at the coarser of the two precisions as written, so a tree file's trailing zeros now count there as a CSV cell's always did, and `0.910` against `0.914` in two JSON files is a `mismatch` where it was `verified` at two places. The extraction digest of a value whose text changed, `0.910` for `0.91`, changes with it. `repro manifest init` proposes a number as the file writes it. `docs/SPEC.md` §3.7 says what the value as stored is for each format; a format that stores numbers in binary has no trailing zeros to recover.
