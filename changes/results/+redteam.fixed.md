**`results claim --frozen-at` names a freeze record, and the record dates the freeze.** Any reference git resolved was accepted, `HEAD` included, and the freeze was dated by its commit date, so a plan frozen after the outcomes were seen, in a commit backdated with `GIT_COMMITTER_DATE`, made a confirmatory claim pass. `--frozen-at` now takes the full commit id a `prereg freeze` record names, and the freeze is placed by the record's position in the ledger, or by its `frozen_at` where it holds none, never by a commit date. `results verify` does the same for claims already in the ledger, and lists a claim citing a commit no record names apart from the protected ones. A confirmatory claim whose run was recorded before the plan was frozen is flagged at the claim and by `verify`, and is not refused.

**A claim's numbers are read against the outputs of the run it names, and a rewritten ledger is caught by its own history.** `results claim` warned of nothing when the sentence printed 0.9913 and the run wrote 0.4213; it now reads the run's outputs as text and warns where a number the claim prints is held by none of them at the printed precision, comparing a stored fraction with a printed percentage only where `%` or `percent` marks it, and `--strict` refuses the claim. An output whose bytes are no longer those the run recorded is not read: `results claim` says so and `verify --files` reports it `CHANGED`. `--derived "how"` records that a claim's numbers are derived from the outputs and exempts them from the comparison. Zero-width, format and other blank characters are removed before numbers are read, with a warning, and an output holding a number with a huge exponent no longer crashes the check. `results verify` counts those claims on one line (`--explain` lists them), lists claims whose run's every output was retired, and `--strict` fails them. An output recorded again under other bytes with no input of the earlier run sealed between the two is warned by `results run` (refused with `--strict`) and reported by `verify --files` as `RERECORDED`, which `--strict` fails; the path is still compared, so a file that also changed since is `CHANGED`. Every re-record of a path is warned, not only the first. Sealing an unrelated file, or sealing an input again with the bytes it had, does not count as a re-run. `results claim` refuses a ledger git history shows was rewritten, on every line of history, so a merge that keeps one side's ledger no longer hides a committed `outcomes seen` event on the other. `verify` fails where a commit holds a version of the ledger or its anchor that the ledger on disk does not extend, `reanchor` refuses in the same case, a deleted timestamp proof is reported, and every `.results/` ledger below the project is verified with it. A sealed tree says which symlinks and cache files its digest skipped. `results coverage` binds a printed number only where a claim prints it with the words around it or the claim's run wrote it, so a claim listing numbers no longer covers a manuscript; it reads values set by simple `\newcommand` and `\def` macros, decimals written `.049`, the Unicode minus and thin-space grouping, and exempts `0.95`, `100` and the other constants only where a formula prints them.

**A freeze record places a freeze only where its plan stands behind it.** A record is placed only where its plan exists and the commit it names holds the plan with the digest it records, so a record with no plan, or edited after the fact, places nothing, and neither does a record whose plan on disk has changed since the freeze. `prereg freeze` writes a `freeze` event into the results ledger, and that event, inside the hash chain, places the freeze; otherwise the position the record states must not be earlier than the ledger as committed at its commit, and where a ledger exists the record's own time places nothing. A record stating a ledger position places the freeze only where the chain holds its freeze event at that position. A freeze made before any ledger existed precedes every ledger event where every commit that touched its record is a strict ancestor of every commit that added the ledger, on every line of history, the record's bytes are ones a non-merge commit wrote, and the plan commit it names precedes that commit, by commit order and never by date; uncommitted, it places nothing.

**A claim on outputs a later run overwrote is unchecked, a restarted ledger is a new chain, and a confirmatory claim's plan is read at every verify.** A second run writing into the same path made a claim the first run did not back read as one nothing could check, and `verify --strict` passed it; `verify` now lists such claims as unchecked, naming the run that rewrote each output, and `--strict` fails them. A ledger deleted in one commit and started again at the same path was reported as `LEDGER HISTORY REWRITTEN`; only versions committed after the latest commit without a ledger are compared, the restart is reported with the commit that made it, and an exposure the earlier chain recorded and the new one does not is named and fails under `--strict`. A ledger replaced in one commit is still a rewrite. `results verify` fails a confirmatory claim whose plan has changed since its freeze, naming the plan and the claim: a plan frozen whole is compared with its record's digest, and one frozen in place by `prereg check`'s rule, so a log entry appended by `prereg log` changes neither. `results claim` on an output edited since its run says so, instead of saying the run records no output it can read as text.

**A restart over recorded work fails a confirmatory claim, and a confirmatory claim's plan is read at its commit, with its companions, and from the ledger where its record is gone.** A restarted ledger is a note only where the chain before it held nothing beyond `init` and `seal`, or where no confirmatory claim follows; otherwise `results verify` fails with `LEDGER RESTARTED OVER A CHAIN WITH RUNS/CLAIMS/EXPOSURES; a confirmatory claim follows`, naming the restart commit. Every exposure the earlier chain held is carried into the ordering of confirmatory claims, placed by the commit that first added it, so a run of the new chain is retrospective as if the exposure were still in the ledger, re-adding the same exposure after the claim changes nothing, and `results claim --confirmatory` refuses such a run without `--anyway`. `verify` holds a confirmatory claim's plan to the commit its record names as well as to its digest, compares the companions frozen with it, and where the claim's `frozen_at` names no freeze record checks the plan against the ledger's `freeze` event at that commit, so rewriting the record's digest or commit, deleting the record, or deleting the plan with it fails the claim. A confirmatory claim naming no freeze is held only to plans in its own project's directory. A claim re-stated in the same words of a later run is no longer listed as unchecked.
